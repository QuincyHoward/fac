# 并行重建流程

## 1. 先分类再并行

| 阶段 | 是否可并行 | 原因 |
|---|---|---|
| 行尾归一化 | 否 | 修改多个全局脚本，且后续 configure 依赖结果 |
| configure | 否 | 生成全局 Makefile 与 `sysdef.h` |
| ABI 宏修正 | 否 | 修改全局头文件，影响所有编译单元 |
| C/Fortran 库编译 | 视构建系统支持 | 可让 `make -j` 处理独立目标，但需确认依赖正确 |
| PFAC 扩展编译 | 条件并行 | 四个扩展可分别调度，但日志与临时目录必须隔离 |
| 导入冒烟检查 | 可并行 | 使用独立 Python 进程，且只读构建产物 |
| demo 回归 | 条件并行 | 有独立输出目录且无同名表冲突时才并行 |
| 写同一基准或同一输出表 | 否 | 文件竞争会污染结果 |

## 2. 推荐调度骨架

```bash
# 串行前置
cd <WORK_ROOT>
# 行尾归一化、configure、sysdef.h 适配按 build-matrix.md 执行

# 可并行阶段：每个任务独立日志
make -j<N> > logs/build_core.log 2>&1 &
python3 setup.py build > logs/build_pfac.log 2>&1 &
wait
```

若工具链或依赖关系不稳定，优先选择较小的 `-j<N>`；构建失败时不要继续叠加并发度。

## 3. 日志与现场保留

- 每个并行任务单独日志：构建、扩展编译、导入检查、demo 回归分别命名。
- 同时记录退出码、开始/结束时间、命令行和环境变量摘要。
- 失败时保留失败日志、部分产物和生成文件；先定位根因，再决定是否清理。
- 不要在失败现场直接重跑 `make clean`，那会丢失定位证据。

## 4. PFAC 并行边界

- PFAC 非线程安全；一个 Python 解释器进程一次只跑一个算例。
- 多算例并行使用独立进程、独立工作目录、独立输出表。
- `openmp` 参数只在脚本显式支持时生效；不要假设所有入口都识别。
- OpenMP 可能改变输出行序；比对时用已有排序逻辑，不要手工重排基准。

## 5. 结果汇总模板

记录以下字段，避免“并行成功”变成无证据断言：

| 字段 | 内容 |
|---|---|
| 任务名 | 构建核心库 / 构建 PFAC / 导入检查 / 单项回归 |
| 命令 | 完整命令行或脚本名 |
| 退出码 | 每个任务单独记录 |
| 日志 | 每个任务独立日志文件 |
| 产物 | 关键文件与大小 |
| 备注 | 是否使用 OpenMP、是否隔离目录、是否有警告 |

## 6. 停止条件

出现以下任一情况立即停止并行扩展：

- 两个任务写同一路径或同一表文件。
- 构建失败但日志归属不清。
- 导入检查出现符号错误或版本错配。
- 回归失败伴随输出目录污染。
- 无法判断差异来自环境还是物理实现。
